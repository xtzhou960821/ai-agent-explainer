AI Agent 是如何思考与行动的？

Agent 不是简单的聊天机器人，而是一套"感知 → 规划 → 行动 → 学习"的自主循环。本页以直觉化的方式，逐层拆解它真正的工作原理。

How It Works

从输入到输出的自主循环

一个 Agent 通常围绕四个阶段循环运转。每一次迭代，它都会比上一次更接近目标——这就是"自主性"的来源。

01

感知与意图理解

Agent 接收用户的目标，结合系统提示词（System Prompt）、对话历史和当前环境状态，把模糊的自然语言转化为结构化的任务。这一步决定了它"要做什么"。

输入解析 · 上下文注入 · 意图识别
02

推理与规划

核心大模型像一个"思考引擎"，把目标分解成可执行的子步骤，选择策略、权衡取舍。高级 Agent 会使用思维链（Chain-of-Thought）或多步规划，把复杂任务拆解成清晰的行动路径。

Chain-of-Thought · 任务分解 · 策略选择
03

行动与工具调用

Agent 不只是"说话"，它通过工具调用（Function Calling）去操作外部世界：查询数据库、调用 API、执行代码、读写文件、控制浏览器。工具的边界，就是 Agent 能力的边界。

Function Calling · API · 代码执行 · 浏览器
04

反馈与学习

执行结果（成功、报错、中间状态）被反馈回模型。Agent 根据反馈调整策略、修正错误、重新尝试，并把关键经验写入记忆，让下一次决策更聪明。

结果反馈 · 错误修正 · 记忆沉淀
Core Components

让 Agent "聪明"的六大组件

大模型只是引擎。真正让 Agent 自主工作的，是这些组件在"大脑"周围的协同配合。

核心大模型

Agent 的"大脑"，负责理解、推理与决策。它并不直接执行任务，而是生成策略、判断下一步做什么。

记忆系统

短期记忆保存当前任务上下文，长期记忆（向量数据库/知识库）让 Agent 跨会话记住经验、偏好与领域知识。

工具调用

连接外部世界的"手"。Agent 通过定义好的工具（API、函数、插件）执行真实操作，突破纯文本输出的局限。

规划引擎

负责把大目标拆解成可执行的小步骤，支持顺序执行、并行分支与动态重规划，让复杂任务得以有序推进。

安全与约束

权限边界、指令遵循、越权防护与人工审批环节，确保 Agent 在可控范围内行动，不会做出危险或越界的决策。

反馈回路

把执行结果回传给模型，形成"行动→评估→调整"的闭环，让 Agent 能从错误中自我修正，持续逼近目标。

Agent Runtime · Harness

Harness：Agent 运行的"舞台"与管家

大模型负责思考，工具负责行动，而 Harness（运行时/宿主）则像导演与舞台总监——把模型、工具、记忆、权限和人工审批组装成一个能持续运行的 Agent 系统。

运行循环编排

Harness 负责驱动"思考 → 行动 → 观察 → 再思考"的循环：调度模型推理、执行工具调用，并把每一步结果喂回给模型，让循环持续到任务完成或触发停止条件。

工具注册与解析

它把可用的 API、函数与插件注册成模型可理解的工具清单，解析模型的函数调用请求，路由到正确的执行器，再把执行结果转化为标准化的观测回传。

状态与上下文管理

它维护会话状态、对话历史与记忆索引，决定哪些上下文该注入、哪些该裁剪，让 Agent 在长任务中保持连贯，同时控制上下文长度与成本。

安全与权限边界

它定义了"哪些工具能碰、哪些操作要审批、输出是否安全"。高风险动作会在 Harness 层被拦截并转交人工审批，自主性始终被约束在可控范围。

错误处理与重试

当工具调用失败、返回异常或模型输出不合法时，Harness 负责捕获、诊断并按策略重试或回退，避免 Agent 因单次失败而直接崩溃。

追踪与可观测性

它记录每一步的思考、工具调用与结果，形成完整的执行日志与回放视图。开发者能据此调试、审计并优化 Agent 的每一步行为。

一句话理解 Harness

如果说大模型是 Agent 的"大脑"、工具是"手脚"，那么 Harness 就是让大脑与手脚协同工作的"身体与指挥中心"——决定思考如何被执行、工具如何被调用、边界如何被守住。

Agent Frameworks

常用 Agent 开发框架

框架是把上述理念落地成工程的关键：它们提供状态图、工具接入、记忆与可观测性等现成能力，让开发者不必从零实现一个 Harness。

LangGraph

把 Agent 流程建模成一张"有状态图"：节点是函数，边是转移逻辑，节点之间共享状态。擅长复杂、可预测的多步骤工作流，适合需要精细控制执行顺序与分支的场景。

Google ADK

Agent Development Kit 提供会话式状态机、多 Agent 协作、跨后端（Gemini、Vertex、Ollama）支持与内置的人机审批机制，主打开发效率与生产级部署。

OpenAI Agents SDK

轻量、以"Agent + Handoffs（交接）"为核心的 Python SDK：支持工具调用、生命周期钩子、追踪与多 Agent 编排，适合快速构建和迭代单 Agent 或简单多 Agent 应用。

CrewAI

以"角色分工"为中心的多 Agent 协作框架：把任务拆给扮演不同角色的 Agent，支持顺序、层级与自主协作模式，适合团队式任务编排。

AutoGen

微软的多 Agent 对话框架：多个 Agent 通过"对话"协作求解问题，强调 Agent 之间的交流与分工，适合研究探索与复杂对话式任务。

LlamaIndex / LlamaAgent

围绕数据与检索构建 Agent：擅长把企业数据、文档与 RAG 流程接入 Agent 工作流，提供数据层能力与 Agent 编排的紧密结合。

SmolAgents

Hugging Face 推出的极简 Agent 库：核心只有"CodeAgent + 工具"。让模型直接写代码作为行动方式，代码即工具调用，兼顾灵活与可读，适合快速原型。

Pydantic AI

以类型安全为核心的 Agent 框架：用 Pydantic 模型定义工具与输出 schema，结构验证开箱即用，类型错误在运行前就能被捕获，适合重视正确性的生产应用。

Microsoft Semantic Kernel

微软面向企业应用的多语言 SDK（C#/Python/Java）：强调"规划器 + 语义内核"与插件体系，与 Azure 生态深度集成，适合已有 .NET/云技术栈的团队。

Deep Dive · LangGraph

LangGraph：把 Agent 画成一张状态图

LangGraph（LangChain 团队出品）把 Agent 流程建模成一张"有状态的有向图"：节点是函数，边是转移逻辑，节点之间共享一份可类型化校验的状态。它让你精确控制每一步的执行顺序、分支与循环。

1

状态（State）：流程的"共享黑板"

用一个 TypedDict 声明整条流程的状态结构，例如是否收到用户输入、检索到的文档、已生成的答案等。所有节点都能读写这份状态，节点之间通过它传递信息。

共享状态 · 类型安全
2

节点（Node）：干活的函数

每个节点就是一个普通 Python 函数：输入当前状态，做自己的事（调模型、查数据库、调用工具），再把更新后的状态返回。函数即节点，零魔法。

函数即节点
3

边与条件边（Edges / Conditional Edges）

普通边定义"无条件从 A 走到 B"；条件边则是"根据当前状态决定下一步去哪个节点"——这正是让 Agent 能自主分支、循环、重试的关键。

自主分支 · 可预测
4

编译与运行（Compile / Stream）

把图编译成可执行对象后即可并行/流式运行。它还内置了持久化（checkpoint）、断点续跑（interrupt）、人工审批与 LangSmith 追踪，天然适合生产级工作流。

可编译 · 可中断 · 可观测
LangGraph Code

代码示例：检索 → 生成 → 评估 的迷你工作流

下面用一个"检索答案 → 判断是否需要追问 → 生成回复"的最小图，演示状态、节点与条件边的写法。

Python · LangGraph
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str                      # 用户问题
    docs: list[str]                    # 检索到的资料
    answer: str = ""                   # 生成的答案

def retrieve(state: State):            # 节点 1：检索
    return {"docs": [f"{state['question']} 的相关资料"]}

def answer(state: State):              # 节点 2：生成
    return {"answer": f"根据 {len(state['docs'])} 份资料总结：" + "要点ABC"}

def route(state: State) -> str:       # 条件边：不够确定就反问
    return "answer" if "资料" in state["docs"][0] else "clarify"

def clarify(state: State):            # 兜底节点
    return {"answer": "请补充更多信息"}

builder = StateGraph(State)
builder.add_node("retrieve", retrieve)
builder.add_node("answer", answer)
builder.add_node("clarify", clarify)
builder.add_edge(START, "retrieve")
builder.add_conditional_edges("retrieve", route, {"answer", "clarify"})
builder.add_edge("answer", END)
builder.add_edge("clarify", END)

graph = builder.compile()              # 编译为可运行对象
print(graph.invoke({"question": "什么是RAG?"}))
Deep Dive · Google ADK

Google ADK：以"会话"为中心的 Agent 框架

Google 的 Agent Development Kit（ADK）把"会话（session）"当作一等公民：所有 Agent 的状态、记忆、工具与审批都挂在一次会话上。它面向生产，强调开发效率、多 Agent 协作与跨后端部署。

1

会话即状态：记忆自动保存

用 InMemoryRunner 或 CloudRunner 创建会话，模型、工具调用结果、Agent 记忆都会写入会话状态。天然支持断点续聊、多轮上下文与人工介入。

会话式状态 · 自动记忆
2

声明式 Agent + 工具

用 Python 类或 dict 声明 Agent，把普通函数一键注册为工具。也内置 MCP 工具支持，能直接接入 Google 生态（Gemini、Vertex、Cloud 工具）与第三方 MCP 服务器。

声明式 · 函数即工具
3

多 Agent 与子 Agent（Sub-agents）

一个 Agent 可以声明 sub_agents，把子任务委派给更专注的 Agent；也可用角色路由实现团队式编排。会话状态让多 Agent 之间共享上下文更自然。

委派协作 · 共享会话
4

内置人机审批与可观测

内置 human-in-the-loop（在工具执行前请求人工确认）、流式输出、与 Vertex AI / Langfuse / OpenTelemetry 集成的追踪，让从原型到生产的路径更顺滑。

人工审批 · 生产级追踪
Google ADK Code

代码示例：一个带工具的客服 Agent

下面用声明式 Agent 对象 + 工具函数 + 会话状态演示 ADK 的核心写法：工具、会话记忆与多 Agent（sub-agents）协作。

Python · Google ADK
from google.adk.agents import Agent
from google.adk.tools import FunctionTool
from google.adk.runners import InMemoryRunner

def check_order(order_id: str) -> str:  # 工具：查订单状态
    return f"订单 {order_id} 状态：已发货"

tool = FunctionTool(func=check_order)

agent = Agent(
    model="gemini-2.0-flash",        # 可换 Vertex / Ollama 等后端
    name="support_bot",
    instruction="你是客服助手，友好且简洁。",
    tools=[tool],                     # 挂载工具
)

runner = InMemoryRunner(agent=agent)   # 会话式运行器
reply = runner.run(
    user_id="u1",
    session_id="s1",
    message="帮我查一下订单 10086",
)
print(reply.message.content)           # 会话记忆自动保留

Frameworks vs Harness

框架与 Harness：联系与区别

这是初学者最容易混淆的一对概念。简单说：框架是"图纸与工具包"，Harness 是"运行的舞台"——框架定义流程怎么写，Harness 决定流程怎么跑。

A

联系：框架内置了 Harness 的能力

LangGraph、ADK、OpenAI Agents SDK 等框架都会内置一套"运行时"：它们自己会驱动思考→行动的循环、管理状态、注册工具、处理错误、提供追踪。也就是说，你用框架时，已经间接拥有了一个可用的 Harness。

框架内置运行时 · 开箱即用
B

区别一：抽象层不同

框架给你的是"高层抽象"——声明状态图、Agent、角色、任务，写得像业务代码；而 Harness 更偏"底层机制"——循环、工具路由、上下文管理、权限拦截。同一个 Harness 概念，在不同框架里的实现与叫法各不相同。

高层编排 vs 底层运行时
C

区别二：框架更强"约束流程"，Harness 更强"运行保障"

框架的核心价值在于编排与复用——它规定了任务如何拆解、Agent 如何协作、状态如何流转；Harness 的核心价值在于运行保障——它负责把模型、工具、记忆、权限真正"跑起来"并守住边界。框架决定流程长什么样，Harness 决定它能否安全、稳定地运转。

编排与复用 vs 运行与保障
D

区别三：框架可变，Harness 是通用概念

框架是你选型的工具（LangGraph 或 ADK 可以互相替换），而 Harness 是一个更通用的概念——你可以自己实现一个最小 Harness（状态循环 + 工具路由 + 权限拦截），也可以直接用框架内置的运行时。理解 Harness，能帮你看透任何框架的底层骨架。

选型工具 vs 通用机制
FAQ

常见问题

聊天机器人通常只做"单轮问答"——你说一句，它回一句。而 Agent 能够理解目标、自主规划、调用外部工具、执行多步操作并自我纠错。它不只是"回复"，而是"做事"。

不是。真正的产品会设置"人机协作"边界：在关键决策、高风险操作或超出权限的任务上，Agent 会停下来请求人工审批。自主性是有范围、有约束的，而不是无限放权。

大模型是 Agent 的"大脑"，但 Agent 本身是一个更完整的系统。它还要靠记忆、工具、规划和安全机制才能真正"行动"。你可以把大模型比作发动机，把 Agent 比作一辆完整的汽车。

原因通常有三类：模型推理出现偏差（幻觉）、工具调用失败（API 报错、数据格式不符）、或规划在复杂场景下"钻牛角尖"。成熟的 Agent 会通过重试机制、结果验证和多轮反馈来缓解这些问题。

Harness 是让 Agent 安全、持续运行的运行时机制：它负责循环、工具调用、状态、权限、重试与追踪；开发框架则是开发者写出这些流程的工具箱和抽象层。许多框架自带 Harness 能力，但两者不等同：前者关注“怎么稳定地跑”，后者也关注“怎么方便地写”。

原型验证和常见流程优先使用框架内置能力：接入快，也能获得成熟的工具路由、状态管理与追踪。只有当你的权限模型、审计要求、工具协议、成本控制或部署环境与框架约束明显冲突时，才考虑自建或深度扩展 Harness；自建意味着也要自己承担测试、监控与故障恢复。

先看任务形态，而不是框架热度：需要精确控制状态、分支与中断时可优先看 LangGraph；想快速搭建以会话和 Google 生态为中心的应用可看 ADK；希望轻量实现工具调用与 Agent 交接可看 OpenAI Agents SDK；任务天然需要明确角色分工时可评估 CrewAI。用一个真实的小任务做原型，比较可控性、调试体验和部署成本后再定型。

优先补齐四类底线能力：为工具设置最小权限和关键操作审批；记录模型、工具和状态的可追溯日志；为超时和可恢复错误设置有上限的重试，为重复调用设置幂等或去重机制，并配置限额与安全停止条件；用真实任务集持续评估质量、成本和延迟。先把“出错时会怎样”设计清楚，才适合把更高的自主权交给 Agent。
